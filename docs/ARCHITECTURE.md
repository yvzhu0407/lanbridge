# 架构与设计原理

本文解释 LANBridge 为什么这样设计。每一条都对应一个具体问题，
不是凭空选型——这些机制是在观察现成联机工具的行为、逐条验证后总结出来的。

---

## 1. 问题拆解

让两个不同网络的人用「局域网模式」联机，需要四件事同时成立：

| 需求 | 谁负责 | 本项目怎么做 |
|---|---|---|
| 两端能互通 | 隧道 | ZeroTier（自建 planet + 私有网络） |
| 知道房间在哪、谁能进 | 协调服务 | 房间服务器（REST + SQLite） |
| 游戏能发现房间 | 广播/组播 | ZeroTier `enableBroadcast` + 网络调优 |
| 游戏流量走隧道 | 路由优先级 | Windows 接口跃点调整（可逆） |

额外加了一项**房间聊天**：在拿到虚拟 IP 之后，成员之间需要一个
「现在谁在线、怎么联系」的通道。它复用同一条 P2P 链路，不额外增加服务器负担。

---

## 2. 控制面 / 数据面分离

**控制面** = 房间服务器。职责只有四个：

1. 用户注册登录；
2. 建房 / 进房 / 离房 / 解散；
3. 在 ZeroTier 控制器上建网络、授权成员；
4. 下发 planet 文件（让客户端连上我们自己的根节点）。

**数据面** = ZeroTier 虚拟网络。所有真实流量（游戏包、聊天）都在这里，
服务器不转发、不存储、看不到。

这样设计的直接收益：

- 服务器挂掉不影响已建立的连接；
- 服务器不需要带宽，只需要偶尔的 API 往返；
- 隐私边界清晰：服务器只知道「谁在哪个房间」，不知道房间里说了什么、玩了什么。

---

## 3. 房间 = 私有网络

选「一房一网」而不是「一个大网按软件分房」，原因：

- **隔离性**：一房一网时，隔离由 ZeroTier 协议保证；大网分房时，隔离全靠应用代码，
  一处判断漏掉就串房。
- **地址稳定**：每个房间独立 `/24`，成员 IP 只由房间内序号决定，重进房间 IP 可复用。
- **成本很低**：控制器上建网络是一次本地 HTTP 调用，几十毫秒，不需要真实资源。

网段规则：

```
10.147.<房间号>.0/24      房间号 1..254
10.147.<房间号>.1  ~ .253 成员地址（由服务端分配）
10.147.<房间号>.253/.254  IP 池上界（控制器分配池）
```

房间号复用：房间关闭后序号可被新房间复用；复用前先清理该序号上的历史记录，
避免唯一索引冲突。

---

## 4. 授权闭环：为什么必须轮询

这是整套流程里最容易写错的一处。

ZeroTier 的成员授权要求：**控制器上已经出现这个节点 ID**，才能对它做
`POST /controller/network/{nwid}/member/{nodeid}`。

时间线：

```
t0  客户端 POST /api/room/join       服务端登记成员、算好 IP
t1  服务端返回 network_id
t2  客户端执行 zt join <network_id>  本地开始加入，状态 REQUESTING_CONFIGURATION
t3  控制器收到成员加入请求，成员以「未授权」形式出现
t4  客户端轮询 /api/join/status      服务端此刻才能授权
```

如果在 t1 就尝试授权，控制器会返回 404——成员还不存在。

而且**授权请求返回 200 不代表成员已生效**。控制器的写入和成员列表的
可读之间有一个短暂窗口，因此 `handleJoinStatus` 里做的是：

```
PUT 授权 → GET 成员列表 → 确认 authorized 字段为 true → 才报告 authorized=true
```

客户端也只在 `authorized && status == "OK" && 有 assignedAddresses`
三者同时成立时才认为「进入房间」。这三道判断任何一道提前放行，
用户都会看到「已进房但 ping 不通」的假成功。

---

## 5. IP 分配

服务端自己维护成员地址，而不是让 ZeroTier 自动分配：

- 地址可预测，方便排障（房间 7 的 3 号成员永远是 `10.147.7.3`）；
- 重新进房时用户保留原 IP，游戏里的直连地址不变；
- 分配时跳过已占用的地址，重新扫描第一个空位。

对应代码：`ipFor(seq, memberSeq)` / `cidrFor(seq)` / `joinInternal` 里的扫描逻辑。

## 6. 房间聊天

### 为什么不用 WebSocket

早期版本尝试过用服务器中转的 WebSocket。问题：

- 消息必须经过服务器，服务器挂掉聊天就断；
- 服务端要维护连接状态，复杂度和资源都上去了；
- 这与「控制面/数据面分离」的原则相悖。

现在改为**浏览器直接 HTTP 到每个成员的虚拟 IP**：

```
发送方 ── POST /chat/send ──► 成员 A 的 8890
         ── POST /chat/send ──► 成员 B 的 8890
         ── POST /chat/send ──► 成员 C 的 8890
```

每个客户端都跑一个 8890 上的小 HTTP 服务（`chat.go`），内存里存最近 500 条。
接收方靠轮询 `/chat/messages` 拉取增量。

### 送达状态

发送方给消息生成一个 ID，每个接收方返回 `{"stored": "<id>"}`。
只有返回的 ID 与发送的 ID 一致才算送达。UI 上的「已送达 n/m」就是这个计数，
未确认的成员会按名字列出，用户能明确看到「谁没收到」。

本机也会存一份用于刷新后可见，但**不计入送达数**。

### 准入校验

```
请求必须满足：
  1. ?net=<网络ID> 是本机已加入、状态为 OK 的网络
  2. 连接的本地 socket 地址 == 该网络分配给我的地址
  3. 来源地址落在该网络的网段内
```

第 2 条是这个设计的关键：用实际 socket 地址而不是 `Host` 头，
所以伪造 `Host` 或 `X-Forwarded-For` 无法把请求导向别的网络。

局限要明说：这是**网络层准入**，不是成员身份认证。同网段的节点可以互访——
这正是我们想要的（游戏本身也是这么工作的），但不要把它当成安全边界。

## 7. 广播与网卡优先级

这两个问题其实是同一件事的两面，必须一起看。

### 广播

局域网游戏发现房间靠的是发往 `255.255.255.255` 或组播地址的 UDP 包。

ZeroTier 侧：控制器上配置 `enableBroadcast: true` 后，**从虚拟网卡发出的**
广播/组播帧会被复制给同网络的其他成员。服务端 `CreateNetwork` 已经带上这个设置。

主机侧：这里有个容易被忽略的点——Windows 上往 `255.255.255.255` 发包时，
系统会按路由表选**一个**出口，而不是每块网卡都发一份。
默认选中跃点最小的那块（通常是物理网卡）。于是游戏的广播包从物理网卡出去了，
虚拟网卡上什么都没有，ZeroTier 自然也没东西可复制。

这就是为什么「降低虚拟网卡跃点」同时解决了**流量选路**和**广播出不去**两个问题：
跃点降下来之后，`255.255.255.255` 的包也会从虚拟网卡发出，ZeroTier 再把它
复制给房间内其他成员，对方的游戏就能看到你的房间。

需要说清的边界：这解决的是「发到虚拟网卡的广播能到达其他成员」。
如果某个游戏**硬绑定**某块物理网卡的 IP 发包（而不是交给路由选路），
降低跃点也拉不回来，那类程序需要额外的抓包重放方案，
本项目不做——代价和风险都太高。

### 网卡优先级

系统按**接口跃点（metric）**选出口，跃点小的优先。ZeroTier 虚拟网卡的
默认跃点往往高于物理网卡，于是游戏流量（和广播）都绕开了虚拟网卡。

解决：进房间后把虚拟网卡的跃点降到 1（`nettune_windows.go`）。

关键约束是**必须可逆**：

```
进房 → 读原跃点 → 记到 nettune-state.json → 设为 1
离房 → 读状态文件 → 恢复原跃点 → 删状态文件
启动 → 若发现残留状态文件（上次异常退出）→ 先恢复
```

状态文件是最后一道保险。即使进程被强杀、用户直接关机，
下次启动时第一件事就是把跃点还原，不会把机器永久改坏。

macOS 不这么做——它没有 metric 概念，出口由**网络服务顺序**决定，
把虚拟网卡提到第一位会影响用户全机上网（可能全部流量绕经隧道），
收益远小于风险。所以 macOS 实现是显式的 no-op，并在代码里写清原因。
macOS 下多数游戏的局域网发现走组播，只要网络开启了广播复制即可工作。

## 8. 客户端形态

### 单文件 + 内嵌 ZeroTier

用户不需要预装 ZeroTier。客户端把 `zerotier-one` 二进制（Windows 还有 TAP 驱动）
嵌入 exe/app，首次运行解压到用户数据目录，拉起一个**独立实例**：

- macOS：`~/Library/Application Support/lanbridge/`，端口 9995
- Windows：`%ProgramData%\lanbridge\`，端口 9995

独立实例的好处：不干扰用户已安装的 ZeroTier（如果有），网络列表互不可见，
卸载时也不会影响系统那个。

### 本地 UI 走 HTTP

客户端本身是个 Go 程序，在 `127.0.0.1:8899` 起 HTTP 服务，UI 是内嵌的单页 HTML。
再用系统 WebView（WKWebView / WebView2）开一个原生窗口。

这样做的原因：

- UI 可以用最熟悉的 Web 技术写，且**不需要构建步骤**；
- 调试时直接用浏览器打开 `http://127.0.0.1:8899` 就行；
- WebView 不可用时自动退回浏览器，不阻塞使用。

### 单实例

启动时先探测 8899 是否已有实例在跑；有的话只唤起窗口然后退出，
避免两个进程抢端口互相打架。

## 9. 生命周期

```
启动
 ├ 迁移旧数据目录（若有）
 ├ 读取 config.json（可选）
 ├ 检查/解压内嵌 ZeroTier
 ├ 启动 ZeroTier 实例（已在跑则跳过）
 ├ 恢复上次残留的网卡跃点
 ├ 启动本地 HTTP（8899）与聊天服务（8890）
 └ 打开窗口

加入房间
 ├ POST /api/room/join       登记成员，拿 network_id
 ├ zt join <network_id>
 ├ 轮询 /api/join/status     直到 authorized 且本地 status=OK 且有 IP
 ├ 拿到网卡名 → 降低跃点（Windows）
 └ 进入房间视图，开始聊天轮询

离开 / 关窗
 ├ POST /api/room/leave
 ├ zt leave all
 └ 恢复网卡跃点
```

## 10. 为什么保留这些扩展点

开源项目要能被人接着改，所以刻意留出边界：

- **聊天 `kind` 字段**：当前只允许 `text`，校验在一处。加文件/图片/表情只要改这里 + 前端渲染。
- **`netTune` 接口**：平台调优是接口实现，加 Linux/新系统只要实现两个方法。
- **`clientConfig`**：客户端可变配置集中在 `~/.lanbridge/config.json`，不改代码即可换服务端。
- **`ZTClient`**：只包了用到的控制器操作；需要更多网络参数时照现有模式加方法。
- **UI 单文件**：改样式、加面板直接编辑 HTML，没有 npm 和打包链。

这些边界都写在代码注释里，见 [EXTENDING.md](EXTENDING.md)。
