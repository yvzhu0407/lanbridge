# 需求：连通性状态可观测性

## 背景

客户端此前无法区分"连不上"的几种不同原因，用户界面上经常出现**显示正常但实际不通**，
或者**把故障归到错误的一方**。已发生的具体问题：

| 现象 | 真实原因 | 用户看到 |
|---|---|---|
| 界面显示绿色 17ms，实际一个包都收不到 | 拿 ZeroTier 隧道延迟冒充 ping | 以为一切正常 |
| 成员表所有成员都显示"已就绪" | 状态判定写死 | 无法判断谁掉线了 |
| 日志里没有任何故障记录 | 只在加入网络时诊断一次 | 事后无从追溯 |
| 排查建议让人去查对方，其实自己网卡没建出来 | 未区分本机故障与对端故障 | 查错方向 |

核心要求：**界面上的每一个连通性结论，都必须来自真实探测，并能落到日志里。**

---

## 术语

三个层次从下到上，任一层不通都会表现为"连不上"，但排查方向完全不同：

| 层 | 含义 | 判据 |
|---|---|---|
| **本机网络** | ZeroTier 是否把虚拟网卡建出来并拿到 IP | `status=OK` 且网卡非空 且 `portError=0` 且 `assignedAddresses` 非空 |
| **隧道** | 两台机器的 ZeroTier 进程之间是否有可用的 UDP 路径 | 直连：`peers` 里有该节点、有新鲜直连路径且 `latency >= 0`；走中继时 `paths` 可能为空、`latency < 0`，此时**以数据面实测为准** |
| **数据面** | 虚拟网卡之间能否真正收发以太帧 | 真实 ICMP 回应，或被拦时 TCP 8890 可连接 |

---

## 需求

### 需求 1：成员连通性探测必须分层

**用户故事**：作为一个玩家，我想知道某个成员到底通不通，以便决定是不是该让对方重启。

#### 验收标准

1. WHEN 本机网络未就绪 THEN 直接返回"本机网络未就绪"，且**不发起任何对端探测**
2. WHEN 本机网络就绪但目标节点不在 `peers` 列表 THEN 返回"链路未建立"，**跳过数据面探测**
3. WHEN 目标节点在 `peers` 但无新鲜直连路径（如走中继，`latency < 0` / `paths` 为空） THEN **必须先实测数据面**：ICMP/TCP 通即判可达；实测也不通才返回"链路协商中"，与"链路未建立"区分
4. WHEN 隧道已通 THEN 发真实 ICMP 探测
5. WHEN ICMP 无回应 THEN 退回 TCP 8890 探测（ICMP 常被防火墙整体拦截）
6. WHEN 隧道通但 ICMP 与 TCP 都不通 THEN 返回"隧道通·数据不通"
7. 探测结果中的 `reachable` 仅在数据面真正可达时为 `true`
8. 探测结果中的 `latency` 在不可达时必须是 `-1`，**不得用隧道延迟填充**
9. WHEN 链路经中继（relay）打通 THEN 必须判为可达并显示真实往返延迟（可能数百毫秒），**不得因 `latency < 0` 误报"协商中/不可达"**

---

### 需求 2：虚拟网络就绪判定必须严格

**用户故事**：作为玩家，我想确信"就绪"二字代表网卡真的能用。

#### 验收标准

1. `status=OK` **不足以**判定就绪
2. 以下任一情况必须判定为未就绪，并给出原因与排查步骤：
   - `portDeviceName` 为空（网卡未创建）
   - `portError != 0`
   - `assignedAddresses` 为空（未拿到 IP）
   - `status` 为 `PORT_ERROR` / `ACCESS_DENIED` / `REQUESTING_CONFIGURATION`
   - `status` 为未知值时

---

### 需求 3：故障必须落日志，且不能刷屏

**用户故事**：作为开发者，我想在用户反馈问题时直接看日志定位，而不是猜。

#### 验收标准

1. WHEN 探测结论为故障 THEN 写入 `client.log`，包含故障描述与排查步骤
2. WHEN 同一目标的故障状态未变化 THEN **不重复写入**
3. WHEN 持续故障 THEN 每 5 分钟提醒一次，避免早期报错被淹没
4. WHEN 故障恢复 THEN 写入一条"已恢复"记录
5. 后台巡检每 90 秒执行一次，**界面未打开时故障同样会记录**
6. 巡检覆盖：ZeroTier 实例未运行、虚拟网络未就绪、planet 不可达、**实例卡死（`join` 接受但网络不进本地列表，自动重启实例）**

---

### 需求 4：界面状态必须反映真实结论

**用户故事**：作为玩家，我不想被一个绿色的数字骗了。

#### 验收标准

1. 成员表「状态」列显示真实探测结论，不得写死
2. 成员表「往返延迟」列：
   - 可达 → 显示真实 ICMP/TCP 往返毫秒数
   - 隧道通但数据不通 → 显示"隧道通·数据不通"，**不得显示绿色延迟**
   - 正在协商 → 显示"协商中"，用橙色（暂态，非故障）
   - 链路未建立 → 显示"不可达"
3. 控制台提供「虚拟网络就绪状态」面板，展示各网络的状态、网卡、分配 IP、planet 可达性
4. WHEN 本机虚拟网络未就绪 THEN 房间页显示原因与排查步骤
5. 顶部状态徽标反映聚合健康结论

---

### 需求 5：排查建议必须指向正确的故障方

**用户故事**：作为玩家，我想照着建议操作就能修好，而不是白忙一场。

#### 验收标准

1. WHEN 本机网络未就绪 THEN 建议只涉及本机，**不得让用户去查对方**
2. WHEN 隧道通但数据不通 THEN 建议指向对方机器（本机无需改动），并说明让对方做反向 ping 验证
3. WHEN 节点已发现但未握手 THEN 建议说明这是刚进房间的正常现象，等待重试，**不得建议"确认对方是否启动"**
4. WHEN 节点不在列表 THEN 建议才涉及"对方可能没启动"

---

### 需求 6：Windows 命令输出必须正确解码

**用户故事**：作为中文 Windows 用户，我想在日志里看到能读懂的错误信息。

#### 验收标准

1. `netsh` / `pnputil` / `taskkill` 输出按系统 ANSI 码页（CP_ACP）解码
2. PowerShell 脚本强制 UTF-8 输出
3. 解码失败时**不得**返回原始字节（Go 会按 UTF-8 解释成乱码），返回合法占位文本
4. 任何情况下写入日志的字符串必须是合法 UTF-8

---

### 需求 7：Windows 网卡定位不能依赖 ZeroTier 别名

**用户故事**：作为开发者，我想让跃点调优在所有 Windows 机器上都能生效。

#### 验收标准

1. 不得假定 `portDeviceName` 等于网卡友好名或接口 GUID
2. 优先按友好名 / GUID 精确匹配
3. 匹配失败时退到按 `InterfaceDescription` 含 `ZeroTier` 或 `zttap300` 定位
4. 定位失败时记录明确日志，说明系统里没有 ZeroTier 适配器

---

## 非功能性需求

### 性能

- 一轮成员测速（N 个成员）对 ZeroTier CLI 的调用次数不随 N 增长（2 秒内共享快照）
- 对端**不在** `peers` 列表时不做数据面探测，避免每个不可达成员消耗超时；但"已发现但无直连路径（中继）"仍需实测，否则会把可达链路误判为不通
- 单成员探测最坏耗时约 2~3.5 秒（ICMP 2s + TCP 1.5s），属必要开销

### 可靠性

- 探测失败不得影响聊天、房间加入等主流程
- CLI 调用失败时不缓存空结果，下次查询重试
- 并发探测下无数据竞争（`-race` 通过）

### 兼容性

- 不改变现有 `/api/ping` 的 `latency` 语义之外的破坏性变更
- 前端兼容旧的数字型 `latency` 返回

### 可观测性

- 每条故障日志都包含：故障描述、隧道/ICMP/TCP 三项结果、可执行的排查步骤
- 日志路径随 `/api/logs` 一起下发给界面

## 验证记录与复盘结论（2026-11-08 真机）

真机用《文明6》联机验证：**两端成功进房、能互相收到对方的 LAN 广播、正常开玩**。
据此确认此前"连不上"的报告多为**诊断显示误判**，链路本身是通的。本次据此修正：

1. **中继链路被误报为"协商中"（假阴性）**——走中继时 ZeroTier 在 LEAF 上不记录直连路径
   （`paths` 为空、`latency < 0`），旧逻辑据此**直接返回"链路协商中"，从未真正发过 ICMP/TCP**，
   日志里的"ICMP/TCP 超时"只是默认 `-1`。已改为：只要节点出现在 `peers` 列表就实测数据面，
   通了即判可达（延迟可能数百毫秒），只有实测也不通才报协商中。
2. **卡死实例不会自愈**——现象：`join` 返回成功，但网络始终不落进 `listnetworks`，自愈只会
   无限重发 `join`。根因：卡死/重复的 `zt-node` 仍在应答 `info`，被误判为健康。已新增自愈动作：
   目标网络持续 ≥2 分钟不在本地列表 → 杀掉实例、重新拉起并补 `join`；重启单独节流（5 分钟）避免抖动。
3. **planet 负延迟但活跃路径仍可达**——存活判据改为"活跃路径最近收到过包"，不再用 `latency >= 0`。

> 直连 vs 中继：本次实测端到端约 330ms，说明走的是 planet 中继。若要降延迟，需打通两端
> UDP 9995 直连（防火墙/NAT），这属于网络环境问题，不在本需求范围内。

## 不在本次范围内

- 中继路径的显式展示与切换（中继**可达性判定**已纳入本次，见需求 1 验收 9）
- 历史连通性趋势与统计
